# Feature Specification: Account-Based Portfolio Tracking

**Feature Branch**: `002-account-based-portfolio`

**Created**: 2026-06-03

**Status**: Draft

**Input**: User description: "포트폴리오 시스템에 계좌별 투자 기록 기능을 추가합니다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 계좌별 포트폴리오 기록 (Priority: P1)

사용자는 여러 투자 계좌(증권 계좌, ISA, IRA 등)를 보유하고 있으며, 각 계좌별로 자산 현황과 보유 종목을 기록하고 싶습니다. 현재는 전체 합계만 기록하지만, 계좌별로 분리된 정보를 통해 자산 배분 현황을 더 명확히 파악하고 싶습니다.

**Why this priority**: 이것이 핵심 기능입니다. 계좌별 데이터 구조가 없으면 다른 모든 기능(차트, 분석, 비교)이 불가능합니다. 사용자의 가장 기본적인 요구사항이며, 독립적인 MVP로서 가치를 제공합니다.

**Independent Test**: 계좌별 데이터 파일(Obsidian 마크다운)을 작성하고, 파서가 이를 정확히 읽어 계좌별 총액과 종목 리스트를 추출하는 단위 테스트로 완전히 검증 가능합니다. 데이터가 올바르게 파싱되면 JSON API를 통해 계좌별 정보가 반환되는지 확인하면 됩니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 계좌별 포맷으로 투자 데이터를 작성했을 때, **When** 시스템이 데이터를 파싱하면, **Then** 각 계좌의 이름과 총액, 보유 종목 리스트가 올바르게 추출되어야 한다
2. **Given** 기존 총액 포맷의 레거시 데이터가 있을 때, **When** 시스템이 데이터를 파싱하면, **Then** 하이브리드 파서가 이를 인식하고 "전체 포트폴리오"라는 기본 계좌로 처리해야 한다
3. **Given** 계좌에 보유 종목이 없을 때(현금만 있는 경우), **When** 시스템이 데이터를 파싱하면, **Then** 종목 리스트는 비어있어야 하며 계좌 정보는 정상적으로 처리되어야 한다

---

### User Story 2 - 계좌별 차트 시각화 (Priority: P2)

사용자는 각 계좌의 가치 추이를 시간에 따라 시각화하여, 어떤 계좌가 성과가 좋은지, 자산이 어떻게 이동되었는지 한눈에 파악하고 싶습니다. 전체 포트폴리오 차트도 중요하지만, 계좌별 분석을 통해 개별 계좌의 성과를 평가할 수 있어야 합니다.

**Why this priority**: 데이터가 파싱된 후 가장 중요한 시각화 기능입니다. 사용자에게 가치를 제공하는 핵심 인터페이스 요소입니다. P1 데이터 구조가 완료되면 즉시 구현할 수 있습니다.

**Independent Test**: E2E 테스트로 계좌별 데이터를 포함하는 테스트 파일을 사용하여, 대시보드에 계좌별 차트가 렌더링되고 올바른 데이터를 표시하는지 확인하면 됩니다. 각 계좌를 선택하여 해당 차트만 표시하는 인터랙션도 테스트할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 여러 계좌의 시계열 데이터가 있을 때, **When** 사용자가 대시보드를 열면, **Then** 전체 합계 차트와 각 계좌별 차트가 표시되어야 한다
2. **Given** 계좌별 차트가 있을 때, **When** 사용자가 특정 계좌를 선택하면, **Then** 해당 계좌의 가치 추이만을 보여주는 차트로 필터링되어야 한다
3. **Given** 계좌별 데이터가 변경되었을 때, **When** 사용자가 새로고침하면, **Then** 차트가 최신 데이터로 업데이트되어야 한다

---

### User Story 3 - 계좌간 비교 및 분석 (Priority: P3)

사용자는 계좌간의 성과를 비교하고, 전체 포트폴리오 대비 각 계좌의 비중(배분 비율)을 파악하여 자산 배분 전략을 검토하고 싶습니다. 또한 특정 계좌의 상세 종목 정보를 드릴다운하여 확인하고 싶습니다.

**Why this priority**: 가치를 더하는 분석 기능이지만, P1, P2가 완료되지 않으면 구현할 수 없습니다. 사용자가 더 깊은 인사이트를 얻을 수 있는 "추가 기능" 성격입니다.

**Independent Test**: 단위 테스트로 배분 비율 계산 로직을 검증하고, E2E 테스트로 드릴다운 인터랙션이 올바르게 작동하는지 확인하면 됩니다.

**Acceptance Scenarios**:

1. **Given** 여러 계좌의 총액 데이터가 있을 때, **When** 시스템이 배분 비율을 계산하면, **Then** 각 계좌의 전체 대비 비중이 퍼센트로 표시되어야 한다
2. **Given** 계좌별 수익률 데이터가 있을 때, **When** 사용자가 비교 보기를 선택하면, **Then** 계좌간 성과(수익률)를 나란히 비교할 수 있어야 한다
3. **Given** 계좌 카드나 차트가 있을 때, **When** 사용자가 계좌를 클릭하면, **Then** 해당 계좌의 상세 종목 리스트가 드릴다운으로 표시되어야 한다

---

### Edge Cases

- 계좌 데이터가 누락되었거나 형식이 잘못된 경우 시스템이 어떻게 처리하는가?
- 레거시 데이터와 새 계좌별 데이터가 혼재된 경우 어떻게 파싱하는가?
- 계좌 이름이 중복된 경우 어떻게 처리하는가?
- 특정 계좌의 데이터가 일부 기간에만 있는 경우(신규 계좌 개설 등) 차트가 어떻게 표시되는가?
- 종목 이름에 특수문자나 공백이 있는 경우 파싱이 올바르게 되는가?
- 계좌 총액과 개별 종목 합계가 일치하지 않는 경우(평가금액 반영 전 등) 어떻게 처리하는가?
- 한 계좌만 있는 경우(기존 총액 기록과 동일한 상황) UI가 어떻게 표시되는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 하나 이상의 투자 계좌를 지원해야 한다
- **FR-002**: 각 계좌는 계좌명, 총액, 보유 종목 리스트를 포함해야 한다
- **FR-003**: 각 종목은 최소한 종목명을 포함해야 한다
- **FR-004**: 시스템은 기존 총액 형식(M.DD 억)과 새 계좌별 형식을 모두 파싱할 수 있어야 한다
- **FR-005**: 시스템은 계좌별 시계열 데이터를 저장하고 조회할 수 있어야 한다
- **FR-006**: 시스템은 계좌별 가치 추이를 시각화할 수 있어야 한다
- **FR-007**: 시스템은 전체 합계와 계좌별 요약을 표시할 수 있어야 한다
- **FR-008**: 사용자는 계좌를 선택하여 상세 종목 정보를 볼 수 있어야 있다
- **FR-009**: 시스템은 계좌간 비교 및 배분 비율을 계산할 수 있어야 있다
- **FR-010**: 시스템은 잘못된 형식의 데이터에 대해 명확한 에러 메시지를 제공해야 한다
- **FR-011**: 레거시 데이터는 새 형식으로 자동 또는 수동으로 마이그레이션될 수 있어야 한다
- **FR-012**: 계좌별 데이터 구조는 Clean Architecture의 Domain 레이어에 정의되어야 한다

### Key Entities

- **투자 계좌 (Investment Account)**: 사용자의 개별 투자 계좌를 나타냄. 계좌명, 계좌 유형(증권/ISA/IRA 등), 총액, 보유 종목 리스트 포함
- **보유 종목 (Holding)**: 계좌가 보유한 개별 자산. 종목명, 수량(선택사항), 평가금액(선택사항) 포함. 현재 버전에서는 종목명만 필수
- **계좌 기록 (Account Record)**: 특정 시점의 계좌 상태. 날짜, 계좌명, 총액, 종목 리스트 포함. 시계열 분석의 기본 단위
- **포트폴리오 스냅샷 (Portfolio Snapshot)**: 특정 날짜의 전체 포트폴리오 상태. 하나 이상의 계좌 기록과 전체 합계 포함

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 기존 총액 기록 방식과 동일한 노력으로 계좌별 데이터를 입력할 수 있어야 한다 (입력 시간 증가 20% 이내)
- **SC-002**: 시스템은 1초 이내에 100개 계좌 x 10년 데이터(약 12,000 레코드)를 파싱할 수 있어야 한다
- **SC-003**: 대시보드는 데이터 로드 후 500ms 이내에 계좌별 차트를 렌더링해야 한다
- **SC-004**: 레거시 데이터 100%가 새 형식으로 무손실 마이그레이션될 수 있어야 한다
- **SC-005**: 사용자는 3번 클릭 이내에 특정 계좌의 상세 종목 정보를 볼 수 있어야 한다
- **SC-006**: 계좌별 파싱 및 API 응답은 95% 이상의 테스트 커버리지를 가져야 한다

## Assumptions

- 사용자는 Obsidian 마크다운 형식으로 데이터를 수동 입력한다
- 계좌 데이터는 읽기 전용이며, 시스템은 데이터를 수정하지 않는다
- 계좌별 종목 수량과 매입 내역은 추후 확장을 위해 고려되지만, 현재 버전에서는 종목명만 필수이다
- 사용자는 토스 스타일의 UI/UX를 기대한다 (명확성, 최소 노이즈, 일관된 인터랙션)
- 데이터 형식은 인간 친화적이어야 하며, JSON 등 기계 형식은 직접 사용하지 않는다
- 마이그레이션 도구는 선택사항이며, 수동 편집도 가능해야 한다
- 계좌 수는 최대 10개까지 지원하도록 설계되며, 이를 초과할 경우 성능 저하가 있을 수 있다
- 기존 시스템의 선형 회귀 예측 기능은 계좌별로도 확장 가능하도록 설계되어야 한다
